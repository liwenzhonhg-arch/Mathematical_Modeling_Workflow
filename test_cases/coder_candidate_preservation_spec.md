# Coder 完整候选保全 Spec

状态：**已实现并通过 r8 真实回归（2026-07-30）**

## 问题

r8 的一次错误反思只返回“把以下函数替换进原文件”的局部补丁。该文本可被 Python
成功执行，但没有主流程，也不会生成 `results.json`。Coder 在执行前就用它覆盖了
`recovery.json`，导致上一个完整候选丢失。

## 规则

1. 反思候选若删除当前完整代码已有的 `results.json`、`sensitivity.json` 或
   `method_runtime.json` 标记，视为退化候选，不替换当前代码、不覆盖 recovery。
2. 移动热反思候选若删除受测模块或可辨识性诊断调用，同样不得替换。
3. 只比较当前候选已经具备的硬输出，不要求旧的简单测试代码凭空增加新文件。
4. 不尝试自动合并 LLM 给出的自然语言补丁；要求下一轮返回完整文件。
5. 反思阶段拒绝局部补丁后，下一次尝试只能把“候选不完整”作为新的失败证据继续
   请求完整文件，不能再次执行旧候选。
6. `recovery.json` 比最新 code 检查点更新且属于当前 active model 时，续跑必须
   先直接执行 recovery；检查点保存时间更新时仍以检查点为准。
7. recovery 必须同时保存同一候选的 `solution.py` 与可选
   `method_contract.json`。恢复执行时同步恢复二者；代码成功后不得因契约丢失退回
   model 的空 `implementation`，也不得仅靠补写 `covers` 伪造覆盖。
8. 从 recovery 或失败 code 检查点进入时，首次恢复执行仍不得调用 LLM；但候选失败
   后的第一次反思必须具备与全新实现相同的题目、模型、参数、数据文件、交付物、
   输出目录和方法契约上下文。不得只发送旧代码与错误后让无上下文 Agent 猜测输入。
9. 长文件反思允许返回 `<artifact name="solution.patch">` 包裹的单文件 unified
   diff。只在旧行、上下文和 hunk 计数全部精确匹配时应用；路径头、命令和自然语言
   替换说明不参与执行。合成后仍按完整候选门禁校验，并只保存完整
   `solution.py`。
10. 代码在计算完硬门禁后主动失败时，异常或 stdout 必须给出失败约束 ID、有限
    实际值和预声明阈值；不得只报告“最终候选失败”。证据若指向现役模型契约而非
    代码错误，应明确 `MODEL_REWORK_REQUIRED`。

## 验收

- 自动测试证明局部补丁不会进入执行列表或 recovery 回调。
- 随后的完整修订仍能正常执行并成为新 recovery。
- 运行失败后的局部反思不会让旧候选在执行列表中重复出现。
- 请求边界暂停后，较新的 recovery 不消耗 LLM 请求即可恢复执行。
- 带方法契约的 recovery 恢复后保留算法类别、覆盖清单和偏差声明。
- 恢复候选成功时仍是零 LLM 请求；恢复候选失败后，测试能在首个修订请求中看到
  原始问题、模型、数据路径和方法契约。
- 精确 unified patch 可合成完整候选；上下文不匹配、计数错误或无 hunk 的补丁被
  拒绝，且不会覆盖 recovery。
- 初次生成、系统提示和错误反思都要求输出可定位的硬门禁证据。
- 现有 Coder 反思测试与全量测试通过。

## 实测结果

- r8 较新的 recovery 在新托管运行中优先于 code v5，未发起 LLM 请求即执行。
- v7 Coder 返回局部补丁后，下一次尝试只记录“候选不完整”，没有重复执行旧代码；
  随后的完整候选才进入执行。
- 针对性回归 `56 passed`，全量回归 `427 passed`。
