# Coder 子问题覆盖真实性 Spec

状态：**已实现；批次 B 公开硬交付物门禁已补齐，待真实 code 续跑验证（2026-08-07）**

## 问题

r8 code v2 只实现问题 1，机器契约门禁正确报告缺少问题 2～4 的硬约束。现有
`implement_with_retry` 遇到“实现未覆盖硬约束”时却只让 LLM 改
`method_contract.json`，不改代码。LLM 把全部约束 ID 填进 `covers` 后，完全相同的
问题 1 代码成为 v3 并通过 code。

solve 随后两次发现 `results.json` 缺少 `q2/q3/q4`，浪费两次 code 重做预算。第二
次 code 修订返回局部补丁，被候选保全规则拒绝后，程序又静默执行旧代码并保存 v4，
造成“修订失败但旧代码成功”的假进展。

## 规则

1. “实现未覆盖硬约束”必须同时修订完整 `solution.py` 和方法契约，禁止只改
   `implementation.covers`。
2. code 候选执行成功后，立即检查分析阶段的每个数值子问题是否存在以
   `<subproblem_id>_` 开头的结果；缺失时在 Coder 内反思，不等 solve 才发现。
3. 标题仅为“建立/构建模型或方法”的纯模型子问题可继续由方法契约证明覆盖；含预测、
   优化、求解或评价的子问题必须有结构化结果。
4. 首次定向修订若返回局部补丁或删除硬结构，旧代码不得被当作本轮修订成功；先产生
   “修订候选不完整”失败，再要求完整修订。
5. 不根据契约声明伪造结果，不放宽现有拟合、可辨识性或可行性门禁。

## 公开硬交付物合同（批次 B）

分析阶段继续使用现有 `deliverables` 字段，不另建平行合同。题面明确要求正式表格时，
条目必须保存可由题面公开信息证明的合同：

```json
{
  "id": "q1_required_table",
  "file": "result1.csv",
  "desc": "按题面固定网格给出结果",
  "source_quote": "题面中证明该交付要求的原文短句",
  "kind": "table",
  "columns": [
    {"name": "x", "unit": "题面单位", "numeric": true},
    {"name": "value", "unit": "题面单位", "numeric": true,
     "monotonic": "nondecreasing"}
  ],
  "row_count": 11,
  "grid": {"column": "x", "start": 0.0, "stop": 10.0, "step": 1.0}
}
```

规则：

1. `file` 必须是安全 basename；它要么逐字出现在题面，要么由逐字出现在题面的
   `source_quote` 完整短句证明；单字或零散词不算证据，禁止 Agent 自行发明硬交付物。
2. `kind: table` 时，`columns`、`row_count` 和 `grid` 是 code/solve 的确定性门禁；
   列名及顺序、行数、固定网格、有限数值和声明的单调性任一不符即失败。
3. `columns[].name` 是实际文件的精确表头，`unit` 是公开单位合同，`numeric` 声明
   该列是否必须为有限数值；系统不从数值大小猜测单位。
4. 正式固定网格不得夹带诊断端点、重复点或网格外行。诊断数据另存普通 CSV，不能
   冒充题面硬交付物。
5. code 候选必须新写出硬交付文件并通过合同后才算成功；solve 再核对当前文件及
   manifest 的路径、SHA256 和同一结构合同。
6. 旧的仅含 `file`/`desc` 条目保持可读，只执行既有存在性、新鲜度和哈希检查。

## 验收

- 自动测试证明缺约束反馈会请求并执行完整新代码，而不是只改契约。
- 缺少 `q2/q3/q4` 的成功进程在 code 输出门禁失败。
- 首次局部修订不会直接执行旧代码并保存成功版本。
- 固定网格表格的缺列、错行数、网格外点、非有限值或单调性错误在 code 阶段失败，
  solve 阶段不能用旧文件或错误 manifest 绕过。
- 全量测试通过，下一轮真实续跑停留在 code 反思，直到四个子问题确实有结果。
