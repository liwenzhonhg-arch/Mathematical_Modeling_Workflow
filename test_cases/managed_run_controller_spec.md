# MMW 托管运行控制器 Spec

状态：**已实现（2026-07-28）**
制定日期：2026-07-28
适用范围：GUI 一键托管、自动修正、机器激活、暂停与恢复

## 1. 问题

当前 GUI 每次只能启动一个阶段，阶段完成后还需要人工审批、再点击下一阶段。
质量门禁已经能阻止许多明显错误，但缺少一个控制器把“运行—检查—定向重做—
激活—下一阶段”连成完整闭环。

目标不是取消质量门禁，而是减少重复点击，并在必须人工判断时才暂停。

## 2. 目标

1. 用户一次确认后，系统可以托管运行到 review、benchmark、compile 和 export。
2. 机器门禁通过时自动激活当前版本并继续。
3. 可修复失败按阶段策略定向重做，不整题从头开始。
4. 达到预算、遇到不可裁决问题或独立验证失败时暂停。
5. 页面刷新后继续显示同一托管任务的状态。
6. 所有机器决策写入现有决策记录，不伪装成人工审批。

## 3. 非目标

- 不绕过 `PipelineStateMachine.quality_error()` 或 `can_approve()`。
- 不把 `scenario-feasible` 显示成 `verified`。
- 不自动补造缺失的现实数据。
- 不自动修改 `.env`、密钥、系统配置或 CI/CD。
- 不无限重试 LLM。
- 不实现多个并行流水线或新的 Agent 编排框架。
- 不在进程崩溃后静默自动继续；只提供显式恢复。

## 4. 运行模式

GUI 保留两种模式：

### 4.1 分阶段审查（默认）

保持现有行为：运行一个阶段，用户检查并审批。

### 4.2 托管运行（显式选择）

用户点击“托管运行到最终交付”，启动前展示：

- 将运行的阶段和最终工具。
- 最大重做次数。
- 时间/调用预算。
- 必停条件。
- 当前模型模式和可信等级边界。

用户确认一次后，控制器可以执行机器激活。该确认不记录为每阶段人工判断；
每个阶段另写 `actor=managed-controller` 的机器决策记录。

## 5. 最小状态机

复用现有 `Job`、`CheckpointManager` 和 `PipelineStateMachine`：

```text
queued
  -> running_stage
  -> checking_gate
      -> activating -> running_stage
      -> repairing -> running_stage
      -> waiting_user
      -> failed
  -> finalizing
  -> completed
```

不建立第二套阶段状态。检查点仍使用：

```text
pending -> completed -> approved
```

GUI 把控制器执行的 `approved` 显示为“托管激活”，不能写成“人工审批”。

## 6. 控制循环

伪流程：

```text
找到下一个阶段
运行阶段
读取最新版本
执行 can_approve + quality_error
  通过：记录机器决策并激活
  可修复：按策略重做，受预算限制
  不可修复：暂停并等待用户
全部阶段完成
运行 benchmark
编译并检查版式
导出 submission.zip
结束
```

控制器必须调用现有阶段入口和审批入口，不复制阶段实现。

## 7. 失败分类

### 7.1 自动修复

仅处理已经有确定修复入口的错误：

- model：Verifier block/warning 的定向修订。
- code：语法、运行时错误、超时、缺产物和当前质量门禁反馈。
- solve：旧结果、缺 JSON、缺交付物、图表 manifest/质量失败。
- paper：缺章节、数值出处、方法契约、引用和版式问题。
- review：数值审计、checklist 和论文定向修订。

每次修复必须：

- 创建新版本。
- 保存错误分类和修复理由。
- 不覆盖已审批历史版本。
- 不重复执行完全相同的失败输入。

solve 门禁若明确指出 `results.json` 子问题缺失或 `sensitivity.json` 无有效扰动，
控制器必须回退并重做 code，再重新运行 solve；不得只重复执行同一份代码。
上游重做后，带 `upstream_changed` 的旧下游版本不得直接重新审批。

### 7.2 必须暂停

- 题目正文无法可靠提取或主问题文件不明确。
- 缺少题面明确要求的原始数据。
- 没有可行解，且修改模型约束需要人工判断。
- 方法契约存在未解释的硬约束缺失。
- 独立 Oracle 或硬不变量失败。
- 生成结果含非有限数值、明显占位或罚函数冒充结果。
- 已达到阶段或总预算。
- `.env`、凭据、系统配置或外部数据需要修改。

暂停时返回：

- 当前阶段和版本。
- 确定性失败原因。
- 已尝试修复次数。
- 建议用户提供的最小信息。
- “修复后恢复托管”按钮。

## 8. 默认预算

启动时允许调整，默认值：

| 项目 | 默认 |
|---|---:|
| 单阶段自动重做 | 2 次 |
| 全流程自动重做 | 8 次 |
| 同一错误重复 | 1 次后停止 |
| 单阶段超时 | 沿用现有阶段超时 |
| 总运行时间 | 默认不限；用户可填总活跃分钟数 |
| API token | 默认不限；用户可填输入与输出 token 合计上限 |

预算达到后状态为 `waiting_user`，不自动降级质量标准。
控制器在每阶段前后重新统计检查点 `meta.json` 中的 token，并以单调时钟累计
跨恢复会话的活跃时长；超限版本不会被自动激活。供应商未返回 token 用量时，
状态明确标记 `token_usage_available=false`，不得伪造用量。

## 9. 决策记录

继续写入现有：

```text
<项目>/.mmw/decisions.jsonl
```

增加兼容字段：

```json
{
  "actor": "managed-controller",
  "policy": "managed-v1",
  "stage": "solve",
  "version": 9,
  "action": "activate",
  "reason": "机器质量门禁通过",
  "gate_snapshot": {
    "quality_error": "",
    "contract": "passed"
  }
}
```

人工审批继续使用 `actor=human`。旧记录没有 `actor` 时按 `human-legacy`
展示，不重写历史记录。

## 10. 任务持久化与恢复

托管状态保存到：

```text
<项目>/.mmw/managed-run.json
```

只保存：

- run ID、policy、阶段、当前版本。
- 预算和已使用次数。
- 状态、时间和安全错误摘要。
- 最后一个已完成动作。

不保存 prompt、LLM 响应、密钥、Codex 命令或 traceback。

进程重启后：

- 不自动执行。
- GUI 显示“存在未完成托管任务”。
- 用户点击“恢复”后重新校验激活版本和门禁，再从安全边界继续。

## 11. GUI

流程总览增加：

- “运行下一阶段”保留。
- “托管运行到最终交付”新增。
- 托管策略和预算确认对话框。
- “暂停等待处理”“恢复托管”状态。

全局任务栏显示：

- 当前阶段、Agent/工具和修复轮次。
- 运行总耗时、当前步骤耗时、最后心跳。
- 已生成最新版本，但任务仍运行时的明确提示。
- 托管激活、人工审批的不同标识。

LLM 阶段继续使用不定进度条，不显示伪造百分比。

## 12. API

沿用当前本机会话令牌和不透明 `project_id`：

```text
POST /api/projects/<id>/managed-run
POST /api/projects/<id>/managed-run/resume
GET  /api/projects/<id>/managed-run
```

启动请求只接受预定义 policy 和数值预算，不能提交命令、绝对路径、prompt
或任意环境变量。

同一项目同时只能存在一个阶段/工具/托管写任务。

## 13. 安全

- 托管模式必须由用户显式开启，不能成为首次启动默认值。
- 机器激活不得伪装成人工判断。
- 浏览器不接收供应商原始响应、密钥或完整异常。
- 所有写 API 继续校验本机会话令牌。
- 参考 Oracle 永远不进入修复 prompt。
- 更新、安装、Git、发布和外部数据修改不属于托管范围。

## 14. 测试要求

最小测试：

- 全部门禁通过时按 8 阶段顺序激活并完成最终工具。
- 一个可修复失败生成新版本后继续。
- 同一失败第二次出现时暂停，不无限循环。
- Oracle 失败时暂停且不向 Agent泄漏期望值。
- 预算耗尽进入 `waiting_user`。
- 恢复时重新校验版本，不复用过期 gate。
- 机器决策和人工决策在记录/UI 中明确区分。
- 同一项目拒绝两个并发写任务。
- 页面刷新后能恢复展示托管状态。

验证命令：

```bash
pytest tests/test_managed_run.py
pytest tests/test_gui.py
pytest tests/test_state_machine.py
pytest tests/
python -m compileall -q mmw
git diff --check
```

## 15. 验收标准

- 用户一次确认后，可以从当前安全阶段运行到 `submission.zip`。
- 所有自动激活都经过现有机器质量门禁并有审计记录。
- 可修复错误定向生成新版本，不整题重跑。
- 不可裁决、独立验证失败或预算耗尽时可靠暂停。
- 刷新页面不丢失运行状态；程序重启后可由用户显式恢复。
- 最终界面分别显示“8 阶段完成”和 `verified/scenario-feasible/unverified`，
  不把流程完成冒充答案正确。
