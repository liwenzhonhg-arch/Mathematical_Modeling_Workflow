# MMW GUI 重做后立即运行 Spec

状态：**源代码已实现并通过自动化与浏览器验证；Windows EXE 打包、发布待单独执行**  
制定日期：2026-07-25  
关联文档：`test_cases/progress_visibility_spec.md`

## 1. 背景

当前阶段审查页的“标记重做”只执行以下动作：

1. 校验人工判断理由。
2. 调用状态机把阶段改回 `pending`。
3. 写入 `.mmw/decisions.jsonl`。
4. 刷新阶段详情和流程摘要。

它不会启动新的后台任务。用户必须再进入“流程总览”，点击“运行下一阶段”。

本轮 `E:\mmw-test` 实测多次出现：

```text
model completed/block
-> 用户填写理由并点击“标记重做”
-> model pending
-> 当前没有任务运行
-> 用户误以为系统已经开始重做
```

这不是状态机错误，而是操作流程没有形成闭环。

## 2. 产品决策

阶段审查页提供两个明确动作：

### 主操作

```text
重做并立即运行
```

- 保存人工重做理由。
- 将目标阶段标记为 `pending`。
- 立即启动该阶段的新后台任务。
- 保持在当前阶段审查页面。
- 自动显示关联任务状态和进度。

### 次操作

```text
仅标记重做
```

- 只修改状态并记录理由。
- 不调用模型，不产生 API/Codex 任务。
- 当前页面立即显示“已标记重做，尚未启动”。
- 同一页面出现“开始重做 <stage>”按钮。

不使用含糊的单一“标记重做”按钮后静默自动运行。按钮名称必须明确告知用户是否会立即调用模型并消耗时间或 API 额度。

## 3. 目标

- 人工发现问题后可以在同一页面完成“说明问题 → 标记重做 → 启动任务”。
- 用户始终知道重做是否已经真正启动。
- 避免在阶段审查页和流程总览之间往返。
- 防止重复点击产生两个后台任务。
- 不绕过人工判断理由、状态机、质量门禁和版本历史。
- 与统一任务进度栏共用同一 Job，不建立第二套运行状态。

## 4. 非目标

- 不自动判断是否应该重做。
- 不在 Verifier 返回 block 后未经人工操作自动消耗下一次模型调用。
- 不自动审批重做后的新版本。
- 不允许同时重做多个阶段。
- 不增加暂停、取消、队列或任务恢复功能。
- 不改变 CLI 的 `rework` 和 `run` 基本语义。

## 5. 页面交互

### 5.1 阶段存在版本且没有任务运行

工具栏显示：

```text
[仅标记重做] [重做并立即运行] [审批并激活]
```

- 有质量门禁 block 时，“审批并激活”保持禁用。
- 两个重做操作均要求至少 4 个字的人工判断理由。
- “重做并立即运行”为主要按钮。

### 5.2 确认弹窗

“重做并立即运行”的确认文案必须包含：

```text
将把 model v6 标记为重做，并立即启动新的 model 任务。
本操作会调用当前配置的模型并产生运行时间或 API 费用。
```

确认按钮：

```text
确认重做并运行
```

取消后不写决策记录、不修改阶段状态、不创建任务。

### 5.3 已标记重做但尚未运行

当前页质量门禁区域上方显示固定状态：

```text
model 已标记重做，当前没有运行任务。
[开始重做 model]
```

用户无需返回流程总览。点击“开始重做 model”直接调用现有阶段启动接口。

该按钮不再要求重复填写理由，因为重做决定已经写入决策记录。

### 5.4 重做任务正在运行

页面显示：

```text
model 正在重做
当前步骤：Verifier 第 N 轮 / 等待 Codex 响应 / 保存检查点
```

- 禁用两个重做按钮和审批按钮。
- 禁用版本切换可能引发的审批操作，但允许只读查看历史版本。
- 页面刷新后自动重新连接同一个 Job。

### 5.5 重做任务完成

- 自动加载最新版本。
- 显示新版本号、Verifier 结论和质量门禁。
- 不自动审批。
- 如果仍为 block，重新启用两个重做操作。

### 5.6 重做任务失败

显示：

```text
重做任务启动成功，但执行失败：<安全错误摘要>
[重新运行 model]
```

阶段继续保持 `pending`，历史版本和重做理由不能丢失。

## 6. 后端行为

### 6.1 API 兼容方案

沿用当前项目操作接口：

```http
POST /api/projects/<project_id>/rework
```

请求体扩展为：

```json
{
  "stage": "model",
  "reason": "具体重做理由",
  "run_immediately": true
}
```

- `run_immediately` 缺失或为 `false` 时保持现有“仅标记重做”行为。
- 为 `true` 时，响应返回新建 Job。

建议响应：

```json
{
  "message": "model 已标记重做并开始运行",
  "affected": ["model", "code", "solve", "paper", "review"],
  "job": {
    "id": "<opaque-job-id>",
    "stage": "model",
    "status": "running"
  }
}
```

### 6.2 操作顺序

“重做并立即运行”必须按以下顺序执行：

1. 校验会话令牌。
2. 校验项目和阶段。
3. 校验人工理由。
4. 检查该项目是否已有运行任务。
5. 检查当前版本是否存在。
6. 检查上游阶段仍满足运行条件。
7. 应用 rework 状态变更。
8. 写入人工决策记录。
9. 在同一临界区登记唯一 Job。
10. 启动后台线程并返回 Job。

第 4～6 步失败时不得修改阶段状态或写入重做决定。

### 6.3 并发与重复点击

- 前端点击后立即禁用确认按钮。
- 后端继续以项目为单位限制一个活动 Job。
- “检查活动任务 → 应用 rework → 登记 Job”必须处于同一锁保护流程。
- 不允许先调用现有 `rework()`、释放锁后再单独调用 `start_run()`，否则双击时可能重复写入决策。
- 如果线程创建后执行失败，Job 进入 `failed`，不能悄悄回到“未运行”。

### 6.4 决策记录

保持现有 `action: "rework"`，增加可选字段：

```json
{
  "action": "rework",
  "run_requested": true,
  "job_id": "<opaque-job-id>"
}
```

不记录 prompt、API Key、Codex 命令或模型响应。

## 7. 与进度 Spec 的关系

本功能依赖 `progress_visibility_spec.md` 中的统一任务状态：

- “重做并立即运行”返回的就是普通 `kind=stage` Job。
- 不新增 `ReworkJob` 类型。
- `running` Job 优先于检查点 `completed` 状态。
- 页面刷新后通过 `running_job` 恢复轮询。
- 重做完成、失败和超时均进入统一任务历史。

如果两个 Spec 分批实施，最低可用顺序为：

1. 先实现同页面“开始重做”按钮和后端原子启动。
2. 再接入完整进度条和持久化状态。

## 8. 状态示例

### 仅标记重做

```text
model v6 completed/block
-> rework
-> model pending
-> 无活动 Job
-> 当前页显示“开始重做 model”
```

### 重做并立即运行

```text
model v6 completed/block
-> rework_and_run
-> model pending + Job running
-> 生成 model v7/v8...
-> Job completed
-> 最新 model completed，等待人工审批
```

### 启动失败

```text
model v6 completed/block
-> rework_and_run
-> model pending + Job failed
-> 当前页保留失败摘要和“重新运行 model”
```

## 9. 安全与边界

- “重做并立即运行”属于明确的模型调用动作，按钮和确认弹窗必须说明。
- 浏览器不能指定任意工作区路径，只能提交后端签发的 `project_id`。
- 修改类请求继续校验本机会话令牌。
- API 不返回供应商原始异常、完整 prompt、Key 或 Codex 会话信息。
- 运行中的阶段禁止审批，避免激活尚未完成的中间检查点。
- 下游受影响范围继续由 `PipelineStateMachine.apply_rework()` 决定，前端不自行推断。

## 10. 验收标准

### 主流程

- 在阶段审查页填写理由并点击“重做并立即运行”，一次确认后创建且只创建一个 Job。
- 用户不需要返回流程总览。
- 当前页在 2 秒内显示运行状态。
- 任务结束后自动加载最新版本。

### 仅标记

- 点击“仅标记重做”后不产生模型调用。
- 当前页明确显示“尚未启动”。
- “开始重做 <stage>”按钮可直接启动正确阶段。

### 并发

- 双击确认按钮不会写入两条决策或创建两个 Job。
- 已有任务运行时，重做请求在修改状态前失败。
- 浏览器刷新不会重复启动任务。

### 失败

- 后台任务失败后，阶段保持 `pending`。
- 当前页显示失败摘要和重新运行入口。
- 历史版本、人工理由和受影响阶段记录仍然存在。

### 审批

- 任何重做任务运行期间都不能审批。
- 新版本仍为 block 时仍不能审批。
- 新版本通过机器门禁后也必须等待人工审批。

## 11. 测试要求

后端测试：

- `run_immediately=false` 保持现有行为。
- `run_immediately=true` 写一条 rework 决策并创建一个 Job。
- 空理由、无版本、上游不满足和已有活动任务时不修改状态。
- 双请求并发时最多一个成功。
- 线程失败后 Job 为 `failed`，阶段为 `pending`。

前端测试：

- 两个重做按钮文案明确。
- 确认弹窗提示会立即调用模型。
- 仅标记后同页出现启动按钮。
- 立即运行后同页进入轮询。
- 运行期间审批和重做按钮禁用。
- 刷新后不重复发起 POST。

验证命令：

```bash
pytest tests/test_gui.py tests/test_state_machine.py
pytest tests/
python -m compileall -q mmw
git diff --check
```

## 12. 实施结果

- 阶段审查页已提供“仅标记重做”“重做并立即运行”和待重做状态下的同页“开始重做”。
- `/rework` 支持 `run_immediately`，在修改状态前检查版本、上游运行条件和活动任务，并返回唯一 Job。
- 决策记录保留 `action=rework`，同时记录 `run_requested` 和可用的 `job_id`。
- 活动任务期间审批和重做按钮禁用，完成后仍需人工审批。
- 已通过 `pytest tests/`、JavaScript 语法检查和 Playwright 页面验证。
- 当前未打包或替换正在使用的 v0.1.4 EXE，也未推送或发布。
