# 请求边界候选保全与实时用量 Spec

状态：**已实现；批次 C 请求前 token/活跃时间双预算门禁已通过自动化回归，待真实预算续跑验证（2026-08-07）**

## 问题

r8 续跑在 `334024/350000` token 时发起一次错误反思。供应商完成响应后累计到
`407707`，现有观察器立即从 `_track_usage` 抛异常，导致已经付费生成的完整响应没有
返回 Coder，也没有写入 recovery。

同一实测还发现 `managed-run.json` 在 code 阶段内部连续 5 次请求期间一直显示
`tokens_used=0`，直到整个 Coder 重试循环返回才更新为 `285225`。请求边界用量没有
实时落盘，GUI 无法展示当前预算状态。

## 规则

1. 每次请求完成后先写调用日志、更新并落盘托管用量，再把完整响应返回调用方。
2. 若本次请求达到预算，允许当前响应被解析、保存 recovery 并执行质量门禁；在发起
   下一次 LLM 请求前抛出 `TokenBudgetExceeded`。
3. 超预算请求产生的检查点不得自动激活；托管控制器在阶段返回后仍按预算暂停。
4. 每次 usage 更新托管进度回调，使 GUI 的 token/耗时摘要不必等待整个阶段结束。
5. 不把 prompt、供应商响应或 Codex 命令写入托管状态。
6. 同一请求前置守卫同时检查 token 和当前会话活跃时间；阶段内部多个 Agent/重试
   请求之间若时间预算已经耗尽，下一次外部请求不得发出。

## 验收

- 第一次请求把累计带过上限后，其响应仍返回并可保存；第二次请求不执行。
- 单次请求后的 `managed-run.json` 已包含最新 token。
- 超限后仍为 `waiting_user`，且超限版本未激活。
- 第一次请求期间耗尽活跃时间预算时，第二次请求在边界前停止。
- 无托管观察器时 API 与 Codex 调用行为不变。
