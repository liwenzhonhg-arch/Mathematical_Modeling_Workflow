# 2010A 独立成品能力修复 SPEC

状态：实施中（A–F 已完成，G 待双轮实测）  
冻结基线：`0ae471c8039ca8b4b4108685f19ba5fe95201cba`  
制定日期：2026-08-03

## 1. 目标与成功定义

目标不是让流水线“八阶段显示完成”，而是让一个新工作区只凭官方题面和附件，在无人补写答案的情况下生成可执行、可核验、可导出的完整作品。

成功必须同时满足：

1. 题面图中的尺寸、标注和相对位置能进入问题文本，不能只提取段落正文。
2. Modeler 只声明当前运行环境与总预算内可执行的模型、约束和验证方法。
3. Verifier 的 block 必须包含可操作的事实错误；托管器在界面/状态中显示首要原因，不能只返回 `RuntimeError`。
4. 单次 model 修订不携带重复的完整历史，token 和时长能按 Agent/阶段追踪。
5. 独立 Oracle 不只检查少数标量，还检查题目要求的完整罐容表。
6. 两个全新 post-fix 工作区均完成 `analyze -> review`、论文编译、视觉门禁和导出，并通过同轮与跨轮重复性检查。

## 2. 已确认的基线缺陷

首轮冻结基线 `benchmark_2010A_clean_r1` 停在 model：

- DOCX 的普通文本提取保留了“1m、2m、6m、1m”等标签，却丢失图中位置，导致 Modeler 把实际油罐圆柱段误写为 `6m`，实际应由尺寸链确定为 `2m + 6m = 8m`。
- 错误几何使 code 得到约 `50.527 m³` 总容积，而独立几何基线约为 `64.664 m³`。
- Verifier 还发现空罐边界、协方差二次型、探针坐标证据和相关误差目标不可执行等问题。
- 托管状态只显示通用 `RuntimeError，请查看工作区日志`，用户看不到首要失败项。
- 17 次 Codex 请求累计约 `826169` tokens；日志没有 Agent 角色和请求耗时，无法定位主要消耗。

这些事实只用于确定修复方向；在第二个冻结基线结束前不得修改运行代码、提示词、知识库或验收范围。

## 4. 实施批次

### A. 完成冻结基线 r2

输入与 r1 相同，预算固定为：

- `1,000,000 tokens`
- `180` 分钟进程活跃时间
- 每阶段最多重做 `2` 次
- 全流程最多重做 `8` 次

结束条件：完成、可信门禁停止、供应商阻塞或预算耗尽。无论结果如何，记录阶段、版本、token、活跃时长、最后结构化证据和成品清单。

### B. 保留 DOCX 图形标注空间关系

修改范围：`mmw/project.py`、对应项目扫描/初始化测试。

实现：

1. 保留现有段落文本提取作为主正文。
2. 从 `word/document.xml` 读取 VML/Word shape 的 `style` 中 `left`、`top`，收集后代 `w:t` 文本。
3. 识别分页标记，按 `page -> top -> left` 排序。
4. 在 `problem.md` 末尾追加“图形定位文本”区块，每行包含页码、横纵坐标和标签文本。
5. 没有定位 shape、样式不完整或单个 shape 解析失败时，仍返回原有正文，不使旧 DOCX 失效。

验收：构造最小 DOCX XML，证明四个标签按横坐标稳定排序；对 2010A 初始化后的 `problem.md`，能明确保留同一水平线上的 `1m | 2m | 6m | 1m` 顺序。

### C. 让 Analyst/Modeler 对图示证据负责

修改范围：`mmw/prompts/system/analyst.j2`、`mmw/prompts/analyze.j2`、`mmw/prompts/system/modeler.j2`、`mmw/prompts/model.j2`、`mmw/prompts/model_revision.j2`、`mmw/prompts/system/verifier.j2`、`mmw/prompts/verify.j2`；仅在现有模板中增加最小规则。

规则：

- Analyst 必须把位置化图示标签解释成尺寸链，并在证据不足时列为待确认，不能任选一个数字当总长度。
- Modeler 必须逐项列出“题面直接给定 / 由尺寸链推导 / 待确认”的几何量。
- Verifier 必须复核总尺寸等式、坐标原点、探针位置和空/满罐边界。
- 相关误差、协方差或置信域只有在代码可直接实现且预算覆盖时才能作为硬约束；否则降为披露或使用可执行的加权残差。
- 不允许为了显得高级而增加题面没有、附件不可辨识的自由参数。

验收：prompt 快照/文本断言覆盖上述关键句；不得出现 2010A 专用数值。

### D. 限制 model 修订上下文膨胀

修改范围：`mmw/pipeline/stage_model.py` 及现有 model 阶段测试。

实现：每次 Verifier block 后，用共享 `LLMClient` 新建一个 `ModelerAgent` 再执行定向修订。这样保留累计真实 usage，但不重复携带前几轮完整对话；修订 prompt 仍显式携带当前模型、结构化 Verifier 证据、题面和必要上游产物。

验收：两轮修订时第二轮 Agent 历史只含系统消息和当前修订请求；版本树、累计 token 元数据和最多两轮规则不变。

### E. 暴露安全、可操作的失败原因与请求进度

修改范围：`mmw/managed_run.py`、`mmw/llm.py`、`mmw/agents/base.py`、GUI 已有任务状态展示，以及对应测试。

实现：

- `BaseAgent` 把角色名写入其 `LLMClient` 的日志上下文。
- 每条 token 日志增加 `role` 与 `duration_seconds`，不记录 prompt、原始响应、密钥或供应商完整异常。
- 托管阶段失败后优先读取已落盘的安全结构化证据：model 的 `verify_status.json`、code 的 `rework_request.json`、状态机 `quality_error`。
- 用户可见错误包含阶段、版本、首要失败项和建议动作；只有没有结构化证据时才回退通用错误。
- 继续复用现有 Job 进度模型；不实现无法从供应商获得的“请求内百分比”。界面显示已用时、累计 token、最近完成请求耗时与当前阶段。

验收：model block 测试返回具体 issue；模拟供应商异常仍不泄露 stderr/prompt；旧 token 日志缺少新字段时读取不报错。

### F. 增加隐藏表格 Oracle

修改范围：`mmw/utils/reference_contract.py`、`mmw/benchmark.py`、`tests/test_benchmark.py`、2010A 的 `reference_expected.json`。

最小 schema：

```json
{
  "tables": [
    {
      "name": "q1_capacity_table",
      "files": ["result1.xlsx", "result1.csv"],
      "height_columns": ["高度", "height_cm"],
      "value_columns": ["罐容", "volume_l"],
      "height_min": 0,
      "height_max": 1.2,
      "step": 0.01,
      "min_coverage": 0.9,
      "monotonic": "nondecreasing",
      "samples": [{"height": 1.2, "min": 3862.74, "max": 4162.74}]
    }
  ]
}
```

通用行为：

- 文件只能从工作区最终成果目录/允许的根目录读取，拒绝绝对路径和路径穿越。
- 只接受 `.csv`、`.xlsx`；复用现有 pandas/openpyxl 依赖，不新增包。
- 列名按声明别名匹配；数值必须有限。
- 高度在 evaluator 内统一为米：原表最大高度不超过 5 时按米，大于 5 且不超过 500 时按厘米，否则按毫米；随后检查覆盖、固定步长、重复高度、单调性和预声明抽样范围。
- 失败写入 benchmark 的 `tables.failures`，任一失败都不能获得 `verified`。
- `reference_expected.json` 仍只由 evaluator 读取，不进入任何提示或检查点。

验收：覆盖正常表、缺行、逆序值、错误抽样点、路径穿越和缺文件六个最小测试。

1. 两轮都完成 8 阶段并审批现役版本。
2. code 与 solve 的规范结果同轮一致。
3. 两张罐容表分别通过覆盖、步长、单调性和抽样值 Oracle。
4. 论文中的结果数值通过出处审计，方法声明与实现一致。
5. PDF 编译和视觉质量门禁通过，无缺字、空白正文页、测试占位内容和无效图表。
6. `submission.zip` 生成，且只包含现役产物。
7. 两轮参数和抽样罐容值满足冻结的跨轮容差。

若任一轮失败，只记录新证据并回到对应最小修复批次；不得改 Oracle 容差来迁就输出。

### G.1 首轮 post-fix 发现的新增根因

`benchmark_2010A_postfix4_r1` 在 code 阶段耗尽 token，形成三条新的通用修复项：

1. LLM 会把真实附件名中的全角标点做 NFKC 归一化，导致 Windows 文件名不存在；执行前必须只把与清单中真实路径等价的归一化文本恢复为磁盘原名，且保存的最终代码也使用原名。
2. 数值门禁不能把名称含 `NRMSE可用`、`R2状态` 的 0/1 状态项当成误差指标本身；状态失败仍由独立状态门禁处理。
3. 容量时间序列只拟合相邻增量会丢掉绝对罐容曲线的几何辨识信息，并诱发无依据的传感器零偏。应改为“初始存量 + 累计净流量”的完整状态轨迹；完整罐容表不得按观测范围裁掉题面要求的端点。

上述修复完成后必须新建下一对工作区；`postfix4_r1` 仅作为失败证据，不计入最终双轮验收。

### G.2 第二轮 post-fix 发现的新增根因

`benchmark_2010A_postfix5_r1` 已通过 code/solve 并正确识别问题二参数，但隐藏表格 Oracle 发现问题一罐容表错误：Modeler 将没有轴向绑定证据的 `1.2 m`、`1.78 m` 直接解释为横向宽度和竖向高度，导致椭圆半轴颠倒。后续版本必须把轴向绑定作为有限候选，用同一附件残差选择，不能读取 Oracle。

同轮 paper 还暴露两个工具问题：Writer/Typesetter 漏写 `L<N>` 注释会触发整篇重生成；“不能证明全局最优”没有被否定词识别。追踪器应从现役契约确定性补齐偏差/局限披露，并扩充否定词；真正的正向全局最优越权继续阻断。

`postfix5_r1` 只作为失败证据；修复后重新冻结并新建下一对工作区。

### G.3 第三轮 post-fix 发现的新增根因

`benchmark_2010A_postfix6_r1` 在 code 阶段用运行证据正确停止：问题一附件的累计进油跨度为 `3.656910 m³`，但现役模型把小罐总长误写为单段 `2.05 m`，几何总容积只有 `3.439101 m³`，任何初始库存平移都无法满足容量边界。

原题图同一尺寸线上是探针两侧相邻段 `0.4 m | 2.05 m`，因此罐体总长应为 `2.45 m`。DOCX 文本框还包含未显示的溢出后缀，旧提取结果为非法单位串 `2.05mcm`，使 Analyst 把本可闭合的尺寸链错误降级为待确认。修复要求：

1. 定位文本中的“数值 + 合法单位 + 额外单位后缀”只保留首个合法数值单位，不把文本框溢出内容并入尺寸标签。
2. Analyst、Modeler、Verifier 对内部探针两侧尺寸执行同一通用规则：总长是两侧相邻段之和，单段不得充当总长。
3. 新版本必须重新创建冻结工作区；`postfix6_r1` 仅作失败证据，不计入最终双轮验收。

### G.4 第四轮 post-fix 发现的新增根因

`benchmark_2010A_postfix8_r1` 首次让修正后的小罐几何进入 solve：总长 `2.45 m`、半轴 `0.89 m/0.60 m`、总容积 `4.110146 m³` 均正确；问题二也得到有符号纵倾 `-2.119490°` 和横偏幅值 `4.237820°`。但隐藏 Oracle 仍判定表格失败：

1. 附件备注明确写有实验初始油量，模型却把各实验段首行重新归零并重估初始存量，造成问题一方向选择错误和约 `0.25–0.59 m³` 的大残差。
2. 两张主表从倾斜后的物理空端开始等间隔，而题目要求的观测油高主网格分别应按名义范围 `0–1.2 m`、`0–3.0 m` 对齐；空满端只能附加，不能替代主表。
3. evaluator-only 契约需要明确支持 `transform=abs`、结果名“横向倾角幅值”和通用 `capacity_L` 列名；这些只修正语义匹配，不改变任何数值范围或抽样容差。
4. 本轮在 paper 阶段达到 1,000,000 token 请求边界。下一对正式工作区预算调整为 **1,500,000 tokens、180 活跃分钟**；质量阈值、Oracle 数值范围和重做次数不变。

上述修复后重新冻结；`postfix8_r1` 为 FAIL / unverified，不计入最终双轮验收。

### G.5 第五轮 post-fix 发现的新增根因

`benchmark_2010A_postfix9_r1` 的两张主表已数值正确：q1 在 `0/0.3/0.6/0.9/1.2 m` 为约 `1.67/595.25/1798.52/3072.43/4012.74 L`，q2 在 `0–3 m` 的七个抽样点全部落入冻结范围；角度制结果为纵倾 `-2.119908°`、横偏幅值 `4.222917°`。新增问题均来自交付与自检边界：

1. 角度结果同时输出 rad 与 deg，旧 alias 顺序先命中 rad；契约补充明确的“角度/角度制”名称，仍使用原冻结范围。
2. 正确表格使用 `q1_capacity_table.csv` / `q2_capacity_table.csv`，列名为 `油位_m` 与 `*_体积_m3`。evaluator 只对明确声明的 `m3/m³` 列执行 `×1000` 换算到 L，不猜测无单位列；Coder 同时被要求输出标准 `height_m` / `capacity_L` 列。
3. Coder 错把 `q2_物理空端容量` 写成 `37.54 m³`，却仍报告约束满足。状态机新增确定性物理门禁：声明的空端/空罐容量不接近零时直接拒绝 code/solve；Coder 必须复算空端为零、满端为总容积。

因此本轮即使主表与角度数值正确，仍为 FAIL / unverified；修复后再次冻结并新建双轮工作区。

### G.6 第六轮 post-fix 发现的新增根因

`benchmark_2010A_postfix10_r1` 在 model v7 被 Verifier 阻断，未进入 code。三次结构化反馈依次发现：主表又从物理空端起步、交叉验证后没有唯一正式参数规则、集中进油行在累计状态与闭合检验中采用矛盾口径。前两项已有规则但首次生成未遵守；第三项的通用修复为：

1. 独立进/出流列中，唯一空白位于另一列明确非零的孤立事件行，且备注、相邻记录和全表口径支持互斥事件时，将空白解释为结构零，不增加无证据的缺失流量平移参数。
2. 证据不足时结构化停止；同一事件不得在累计状态中计入、在闭合检验中排除。
3. 训练/留出与交叉验证只负责候选选择和诊断；选定结构后必须按预声明规则全数据重拟合或选出唯一正式候选，再生成参数和表格。

本轮为 FAIL / unverified，不计最终双轮；修复后重新冻结。

### G.7 第七轮 post-fix 发现的新增根因

`benchmark_2010A_postfix11_r1` 已通过 code/solve，通用物理门禁 PASS，且真实附件拟合得到纵倾 `-2.125315°`、横偏幅值 `4.243263°`。独立 benchmark 与 paper 暴露三项交付契约问题：

1. `q2_横向偏转角` 是合法且单位明确的结果名，但隐藏契约缺少该纯语义 alias；只补别名，不改变冻结数值范围、变换或容差。
2. 两张正式容量表数值与题面主网格正确，却把网格外物理空满读数插入同一 CSV，触发 `duplicate_or_off_grid_height`。正式必答表文件只能包含题面名义固定网格；离网格端点另存诊断结果或单独文件。
3. paper 首次生成因出现越权的“全局最优”字面表述被确定性追踪门禁拒绝，整篇重做后在 `1,510,942` tokens 处暂停。方法契约不允许全局声明时 Writer 连否定句也不用该字面短语；下一对冻结工作区预算提高为 **2,000,000 tokens、180 活跃分钟**，最优性门禁和重做次数不变。

本轮为 FAIL / unverified，`postfix11_r2` 不启动；修复后以新提交重新创建双轮工作区。

### G.8 第八轮 post-fix 发现的新增根因

`benchmark_2010A_postfix12_r1` 在 model v7 被 Verifier 阻断，未进入 code。模型把偏心探针下的纵倾正负候选分别减去各自初始存量后比较，并据此把相差常数平移的绝对罐容曲线误判为物理等价。

通用修复边界为：只有探针位于相应对称面，或正负倾角在题面完整制表网格上的**绝对容量曲线**经独立计算一致时，才能折叠为幅值参数；不得用各自初始存量、零偏或常数平移消除差异。偏心探针默认保留有符号倾角。
