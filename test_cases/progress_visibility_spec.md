# MMW GUI 统一任务进度与完成态 Spec

状态：**源代码已实现并通过自动化与浏览器验证；Windows EXE 打包、发布待单独执行**  
制定日期：2026-07-25  
适用范围：GUI 阶段运行、质量工具、论文编译、最终导出和 Windows 一键更新

## 1. 背景与问题

当前 GUI 能启动后台任务并轮询 `Job.status`，但用户仍无法可靠回答以下问题：

1. 任务是否真的还在运行。
2. 当前正在做什么，已经持续多久。
3. 阶段目录出现新检查点后，整个任务是否已经完成。
4. 页面刷新后，是否仍在跟踪原来的后台任务。
5. 更新、审计、Benchmark、编译和导出进行到了哪一步。
6. 任务失败后，失败状态和原因去哪里查看。

本轮实测已出现典型冲突：`model` 在生成中间检查点后，阶段卡片显示
`completed`，但 GUI 后台任务和 Codex Verifier 仍在运行。检查点状态表达
“已有一版产物”，后台任务状态表达“本次完整操作是否结束”，两者不能混为一谈。

## 2. 目标

- 在所有 GUI 页面持续显示当前任务、当前步骤、耗时和最终结果。
- 明确区分“已有检查点”和“本次后台任务已完成”。
- 对可计算的工作显示真实百分比；对不可计算的 LLM 推理不伪造百分比。
- 页面刷新后自动重新连接当前任务。
- 后台任务运行期间禁止审批对应阶段。
- 完成、失败和超时结果可在刷新后继续查看。
- 不向浏览器、日志或项目文件暴露 API Key、Codex 登录态、prompt 或供应商原始响应。

## 3. 非目标

- 不预测 LLM/Codex 的剩余生成时间。
- 不根据历史耗时生成看似精确的虚假百分比。
- 不增加暂停、取消或进程退出后的自动续跑能力。
- 不改变八阶段质量门禁、审批规则和 Agent 提示词。
- 不把 token 流、模型思考过程或完整异常正文返回浏览器。
- 不为进度条引入新的前端框架或运行时依赖。

## 4. 状态优先级

页面展示必须遵守以下优先级：

1. 当前阶段存在 `running` 后台任务：显示 `running`，即使已经生成新检查点。
2. 后台任务结束且生成检查点：显示检查点的 `completed` 或 `approved`。
3. 后台任务失败且没有新检查点：显示 `failed`，并保留安全错误摘要。
4. 没有后台任务和检查点：显示 `pending`。

审批按钮只有同时满足以下条件时才能启用：

- 对应阶段不存在运行中的后台任务。
- 已选择有效检查点版本。
- 机器质量门禁允许审批。

## 5. 后台任务数据合同

现有 `Job` 在保持 `id`、`workspace`、`stage`、`status`、`message`、
`started_at` 和 `finished_at` 兼容的基础上增加：

| 字段 | 类型 | 含义 |
|---|---|---|
| `kind` | `stage/tool/update` | 任务类别 |
| `progress_mode` | `determinate/indeterminate` | 是否存在真实百分比 |
| `progress` | `0..100/null` | 仅在可计算时返回 |
| `current_step` | string | 当前步骤的用户可读名称 |
| `step_index` | integer | 已进入的步骤序号 |
| `step_total` | integer/null | 已知步骤总数 |
| `updated_at` | datetime | 最近一次步骤或进度更新 |
| `result` | object/null | 完成后的脱敏结果摘要 |

合法状态流转：

```text
queued -> running -> completed
                  -> failed
                  -> timed_out
```

`completed` 只能在整个后台函数返回并完成最终写盘后设置，不能在生成中间检查点时提前设置。

## 6. 各任务的进度语义

### 6.1 LLM 与 Codex 阶段

LLM 推理没有可信的总 token 数和剩余时间，因此使用不定进度条：

```text
准备输入
调用 Analyst/Modeler/Coder 等 Agent
等待 Codex 或 API 响应
解析并校验产物
保存检查点
执行阶段质量门禁
完成
```

界面显示当前步骤、本步骤已持续时间和任务总耗时，不显示伪造的
“67%”或“预计还需 3 分钟”。

`model` 的自动修订需要额外显示：

```text
Modeler 生成候选
Verifier 第 N 轮验证
Modeler 第 N 轮修订
保存 vN 检查点
```

无法事先确定最终修订轮次时，`step_total` 为空。

### 6.2 数值审计与 Benchmark

- 数值审计：加载结果 → 扫描论文数值 → 汇总高置信问题 → 写入报告。
- Benchmark：加载绑定版本 → 执行场景/Oracle → 核对不变量 → 计算可信等级 → 写入报告。

步骤可确定，但单步耗时不可准确预测，默认使用不定进度条和步骤序号。

### 6.3 论文编译

显示确定步骤：

```text
检查 LaTeX 环境
组装论文
XeLaTeX 第 1 轮
XeLaTeX 第 2 轮
检查 PDF
完成
```

除非编译器能提供可靠的文件总量，否则不显示基于时间推算的百分比。

### 6.4 最终导出

显示：

```text
执行导出前门禁
收集提交文件
生成 submission.zip
核对文件清单
完成
```

压缩阶段可按已处理文件数或字节数显示真实百分比。

### 6.5 Windows 一键更新

更新任务必须提供真实下载进度：

```text
检查最新 Release
下载 ZIP：已下载字节 / 总字节
校验 SHA256
安全检查 ZIP
解压到新版本目录
启动新版本
```

- 下载百分比只能来自实际读取字节数和 Release 资产大小。
- SHA256 校验、路径穿越检查和解压体积限制保持现有安全要求。
- 校验失败时不得解压、安装或重启。
- 页面在新进程启动前显示明确的“即将重启”状态。

## 7. 后端实现约束

### 7.1 进度报告器

新增一个最小的可选进度报告器，建议放在 `mmw/utils/progress.py`：

- GUI 后台线程安装真实 reporter。
- CLI 默认使用 no-op reporter，不改变现有命令接口。
- 阶段、LLM 调用、验证器、编译器和更新器只报告已知步骤。
- reporter 更新同一 `Job`，不得另建平行任务状态系统。

### 7.2 API

- `GET /api/jobs/<job_id>` 返回扩展后的 Job 数据。
- `GET /api/projects/<project_id>` 继续返回 `running_job`，并增加最近一次任务摘要。
- 页面启动或刷新时，如果存在 `running_job`，自动恢复轮询。
- 任务写操作继续要求当前本机会话令牌。

### 7.3 任务结果持久化

- 项目任务最终状态追加到 `<项目>/.mmw/logs/jobs.jsonl`。
- 更新任务最终状态保存在 `%APPDATA%\MMW\jobs.jsonl`。
- 仅保存任务类型、阶段、步骤、时间、状态和脱敏消息。
- 不保存 prompt、供应商响应、API Key、Codex 命令输入或完整 traceback。
- 文件只用于展示最近状态，不作为断点续跑来源。

## 8. 前端规格

### 8.1 全局任务栏

在主内容区顶部固定展示：

- 任务名称，例如“数学建模 · Verifier 第 2 轮”。
- 状态：排队、运行、完成、失败、超时。
- 进度条。
- 当前步骤。
- 本步骤耗时和任务总耗时。
- 最近更新时间。

无任务时任务栏折叠为“当前无运行任务”。

### 8.2 阶段卡片与审批页

- 运行中的阶段卡片显示 `running`，覆盖检查点的 `completed` 标记。
- 已产生中间版本时显示“已生成 vN，任务仍在运行”。
- 审批页显示同一任务栏，并禁用“审批并激活”和“标记重做”。
- 任务结束后自动刷新版本、产物、质量门禁和审批按钮。

### 8.3 刷新与轮询

- `boot()` 恢复项目后立即读取项目摘要。
- 发现 `running_job` 时自动调用 `pollJob()`。
- 同一页面只允许一个轮询循环，避免刷新或导航产生重复请求。
- 轮询间隔默认 1.5 秒；连续网络错误时退避，但不把网络错误误报为任务失败。

### 8.4 完成与失败

- Toast 只做即时提醒，不能作为唯一状态载体。
- 完成后任务栏保留完成摘要，直到用户开始下一任务或主动收起。
- 失败/超时后显示安全错误摘要和日志入口。
- 页面刷新后仍能看到最近一次失败，而不是重新显示“未运行”。

## 9. 安全与隐私

- 进度文本必须来自程序预定义步骤，不直接转发模型输出。
- 未知异常只展示异常类型和安全错误码。
- Codex CLI 命令行不得包含在浏览器响应和持久化任务日志中。
- 更新下载地址继续限制为官方 GitHub Release。
- 项目路径继续由后端不透明 `project_id` 绑定，不新增任意绝对路径 API。

## 10. 验收标准

### 阶段运行

- `model` 生成中间检查点后，卡片仍显示 `running`，审批按钮保持禁用。
- Codex 调用期间显示不定进度条、当前角色和持续时间，不显示虚假百分比。
- 后台线程结束后才切换为 `completed` 或 `failed`。

### 页面刷新

- 运行中刷新浏览器，5 秒内恢复同一任务的步骤、状态和耗时。
- 不出现重复轮询、重复 Toast 或“任务不存在”。

### 更新

- 下载过程中百分比随真实字节数递增。
- SHA256 不匹配时显示失败，旧版本继续运行。
- 安装完成后显示重启步骤并进入新版本。

### 工具

- audit、benchmark、compile、export 均显示当前步骤。
- 失败后刷新页面仍能看到最后失败状态。

### 兼容性

- CLI 八阶段流程和输出目录不改变。
- OpenAI-compatible API 与 Codex 两种模式都能运行。
- 不新增前端构建步骤、CDN 或全局依赖。

## 11. 测试要求

最小新增测试：

- Job 合法状态流转和进度范围校验。
- 运行中检查点不能让 GUI 提前显示完成。
- 运行中禁止审批。
- 刷新后能从 `running_job` 恢复轮询。
- LLM 任务不返回伪百分比。
- 更新下载回调按真实字节更新进度。
- SHA256 失败时不解压、不重启。
- jobs.jsonl 不包含 prompt、Key 和供应商响应。
- audit、benchmark、compile、export 的步骤状态可查询。

验证命令：

```bash
pytest tests/test_gui.py tests/test_update.py
pytest tests/
python -m compileall -q mmw
git diff --check
```

浏览器验证：

- 使用 Playwright 覆盖阶段运行、页面刷新、任务完成和失败。
- 使用可控的本地假更新资产验证下载、校验、解压和重启前状态。
- 不用真实 API Key 或用户 Codex 会话作为自动化测试夹具。

## 13. 实施结果

- `Job` 已统一提供任务类型、步骤、进度模式、开始/更新时间、结束状态和安全结果摘要。
- 阶段、质量工具、编译、导出与更新共用全局任务栏；LLM 阶段使用不确定进度，更新下载使用真实百分比。
- 工作区摘要和更新接口会返回活动 Job，浏览器刷新后恢复轮询；最终状态写入本机 `jobs.jsonl`。
- 运行中的 Job 覆盖检查点完成态，阶段运行期间禁用审批和重做操作。
- 已通过 `pytest tests/`、JavaScript 语法检查和 Playwright 页面验证。
- 当前未打包或替换正在使用的 v0.1.4 EXE，也未推送或发布。
